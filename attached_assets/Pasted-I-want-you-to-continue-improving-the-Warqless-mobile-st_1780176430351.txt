2. MOBILE CONTENT PROTECTION — VERY IMPORTANT
=============================================

Now I want to start working on the content protection side for the phone app.

The most important rule:
A purchased book must NOT be downloadable in any direct way.

The student should never receive:

* a PDF download button
* a public file URL
* an exposed direct file link
* a raw PDF file
* any easy way to export the book file

The book should only open inside the Warqless reader.

For the MVP/demo, implement the structure and UI/logic as much as possible, even if some parts are still simulated.

4. ONE DEVICE ONLY — NOT EMAIL, NOT PHONE, DEVICE
=================================================

This is extremely important.

The account/book access must be locked to ONE DEVICE ONLY.

I do not mean one email.
I do not mean one phone number.
I mean ONE PHYSICAL DEVICE.

A student account should not be able to open the app/books on multiple devices.

Rules:

* On first successful login, register the current device as the account’s primary device.
* After that, the same account should only work on that same registered device.
* If the user logs in from another device, block access.
* Show a clear message:
  Arabic:
  “هذا الحساب مرتبط بجهاز آخر. لا يمكن فتح الحساب إلا من جهاز واحد فقط.”
  English:
  “This account is linked to another device. It can only be used on one device.”

Device lock should be based on a device identifier/fingerprint, not just email or phone.

For MVP/demo:
If a true device fingerprint is not available in the current stack, create a clean device identity layer:

* getCurrentDeviceId()
* registerPrimaryDevice()
* verifyPrimaryDevice()
* blockIfDifferentDevice()

Use available Expo/React Native device APIs if already installed.
If new package is required, explain before installing.
If packages are not available, create a temporary demo device ID stored locally, but structure the code so it can later be replaced with real device fingerprinting.

Important:
Comment clearly that true production-grade device fingerprinting must be implemented with backend verification and secure device identifiers later.

5. DEVICE ACCESS FLOW
=====================

Implement or prepare this flow:

First login:

1. Student logs in.
2. App checks if the user has a registered primary device.
3. If no primary device exists, register current device as primary.
4. Allow access.

Next login from same device:

1. Student logs in.
2. App compares current device ID with registered primary device ID.
3. If it matches, allow access.

Login from another device:

1. Student logs in.
2. App compares current device ID with registered primary device ID.
3. If it does not match, block access.
4. Show message:
   “This account is already linked to another device.”

Device reset:
Do not allow automatic reset now.
Instead, show:
Arabic:
“لتغيير الجهاز، تواصل مع الدعم الفني.”
English:
“To change your device, please contact support.”

Later, admin/support can approve device reset.

===========================

Before opening any book in the reader, check:

* User is logged in
* User role is student
* Internet connection is available
* Device is authorized
* Book is purchased or borrowed
* License is valid
* Book is not currently lent out by the owner

For MVP/demo:
If real licenses are not implemented, simulate the checks using local purchasedBooks/mock library state.

Important:
Remove any behavior that allows opening a book directly from the reader route without purchase/library ownership.

If the user tries to open:

  “You cannot open this book. You must purchase or borrow it first.”
